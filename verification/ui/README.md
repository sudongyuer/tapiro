# UI verification

Offline, deterministic UI checks on the iOS Simulator. A verify build (`EXPO_PUBLIC_UI_VERIFY=1`,
Release) runs without network or login; each case drives the real UI with AXe, asserts on the
accessibility tree, and captures screenshots and video in light and dark.

```bash
bun run verify:build          # prebuild if needed, Release build into .verify/DerivedData
bun run verify:ui             # all cases, light + dark → .verify/ui/<locale>/<appearance>/<case>/
bun run verify:smoke          # app_launches, sign_in_fixture, shell_tabs, home_one_card; zh-Hans light
bun run verify:ui --affected  # cases whose DEPS meet the diff against main; zh-Hans light
bun run verify:ui --affected --base main --dark --locales   # also dark, also en and each case's LOCALES
bun run verify:full           # the full matrix: every case, light + dark, zh-Hans + en + every declared locale
bun run verify:ui design_tokens --appearance dark   # named cases run zh-Hans; add --locales or --locale en
bun run verify:clean
```

The runner owns three named Simulators, `Tapiro Verify`, `Tapiro Verify 2` and `Tapiro Verify 3` (iPhone 17 Pro,
newest iOS runtime), creates each once if missing, and hands the runs to them from one queue; `--workers N` sets how many
it uses, and `--udid` runs on one given Simulator. Before booting more than one it checks that the disk holding the
checkout has at least 15 GB free and otherwise runs on `Tapiro Verify` alone, printing why (`pool.py`,
`python3 -m unittest test_pool`). The extra Simulators shut down when the run ends. The breaker below counts each
Simulator's runs on their own. Never create Simulators or pass another DerivedData path yourself.
`--affected` collects `git diff --name-only <base>...HEAD`, uncommitted changes and untracked files, and
picks each case whose `DEPS` prefixes (or its own file) match one, printing why. A change to shared code
(`affected.SHARED`: `src/ui/`, `src/lib/`, the root layout and index route, the Debug scenes (`src/debug/`, `src/app/debug/`), `modules/`, `plugins/`, `assets/`,
`app.json`, `package.json`, `bun.lock`, `tsconfig.json`, the runner, driver, selector, breaker, recording and Swift tool helpers, build script and string export)
picks every case; a case without `DEPS` always runs. Smoke and affected run zh-Hans light unless `--dark` or
`--locales` is given; the PR gate is smoke plus affected, and the full matrix runs when the machine is idle and
before TestFlight. `python3 -m unittest test_affected test_breaker test_pool` in `verification/ui` covers the selection (and
checks that every case declares `DEPS` that match real paths); CI runs it.
Cases launch in `zh-Hans` (`-AppleLanguages`). The language order is zh-Hans > en > ms:
a PR run uses zh-Hans, a milestone run (`--locales`, and the full matrix) adds `en` for every case, and `ms` exists
only to catch truncation of the longest copy, so a case that shows long copy declares
`LOCALES = ['zh-Hans', 'ms']` and runs Malay at milestones. A case never needs to declare `en`.

App copy is never typed into a case. `run.py` runs `scripts/export-ui-strings.ts` once per invocation, which writes
every locale's strings (the `src/lib/i18n/locales` objects flattened by dotted key, the native permission strings
under `native.ios.*`, and `languages.<code>` for the picker names) to `.verify/ui-strings.json`. A case asserts copy
with `ui.t('pay.sheet.payTo', name='阿杰')` (i18next `{{name}}` interpolation, locale of the run); `ui.t_in(locale, key)` reads
another locale, `ui.tagged(key, 'terms')` returns the text inside a `<terms>` tag, `ui.pattern(key, amount=r'\d+')` builds a
regex from a string with placeholders, and `ui.other_locale()` gives a different language to switch to. A missing key raises,
so a renamed string fails the case instead of falling back. Fixture data (names such as 小林, task titles, amounts) stays
literal in the case. `ARGS = [...]` adds
launch arguments, such as `-uiVerifyShellFeed <kinds>` to choose the live items (omitted: all
four; `none`: calm; the bounty cards `bountyAction`, `bountyWaiting` and `bountyOneTime` are opt-in beside
`bountyInProgress`, and home records each one-time card it marks seen as a JSON array in the defaults key
`uiVerifyHomeSeen`, cleared at launch) and `-uiVerifyFixture worst|one|empty` to swap the fixture data behind the
same items, the 消息 badge, the fixture user's name and the seeded payee methods (`worst`: 40-character names, long routes,
RM 12,345.60, 1,284 unread; `one`: `Jo`, RM 0.50, 1 minute, 1 unread; `empty`: no payee methods; `worst` also seeds seven payee methods with long names).
`-uiVerifyPayMethods all|wallets|alipay|duitnow|cash|none` picks the payee methods the pay sheet shows (default `all`), `-uiVerifyPayment <id>` opens the `pay-sheet` scene on `fixture-owe` (default, payer), `fixture-owed` (payee, marked paid) or `fixture-owed-cash` (payee, due, takes cash), `-uiVerifyStickers none|one|seven|worst` seeds the fixture sticker book (default `none`, so the next settle is the first; `worst` has seven long titles) and every fixture settle adds one sticker, so the celebration count and the book agree, `-uiVerifyFx none` removes the fixture BNM rate, and `-uiVerifyPaymentsFail 1` fails the first payments load. The bounty post fixture service reads `-uiVerifyPostCost free|last|coin|none` (2/3 free left, 1/3, 0 free and 4 coins, nothing left; default `free`), `-uiVerifyUnpaid none|two|old` (two unpaid payments, 阿杰 RM 15 and Lily RM 6, or one 8 days old; both block publishing; with `-uiVerifyFixture worst` the names are 40 characters and RM 12,345.60), `-uiVerifyPublish ok|failOnce|fail|alreadySent` (`alreadySent` answers that the draft's id already went out), `-uiVerifyDraftSent 1` (the first draft the form checks counts as already published), `-uiVerifyStatusFail 1` (the first cost/blocked status load fails; the 「+」 hint consumes it, so cases that need the failure start on the `bounty-confirm` scene) and `-uiVerifyBountyDraft none|demo|one|worst` (seeds the fixture user's stored draft at launch: `none` clears it, `demo` is the parcel errand due 18:00, `one` is RM 1 without optional rows, `worst` sits on every limit; omitted, the stored draft is kept, which is how the relaunch checks work). The fixture payments replace the money kinds of the shell feed, so `oweMoney` and `owedToYou` come from the payment fixture. Saving to Photos is replaced at the device boundary; the QR image itself is drawn by the kit.
`-uiVerifyBoard full|one|empty|long|worst` picks the fixture board under home (default `full`: twelve bounties, which keeps home scrollable for the home and shell cases; `one`: one non-urgent bounty; `empty`: none; `long`: 45 bounties over three pages, five without a place; `worst`: 45 bounties on every limit), and `-uiVerifyBoardFail none|first|refresh|page` fails the first load, the first refresh after it, or the first next-page request once (default `none`).
`-uiVerifyLocation granted|undetermined|undeterminedDeny|denied|reduced|noFix` replaces the location service (default `granted` at Sunway Pyramid 3.0733, 101.6078; `undetermined` answers the permission request with 允许 and `undeterminedDeny` with 不允许 without drawing the system alert; `reduced` is granted with approximate accuracy; `noFix` is granted without a position). `-uiVerifyApply ok|failOnce|taken|closed|gone` answers the fixture `apply` (with `-uiVerifyFixture empty` there is no payee method and `apply` answers `noPayee`); in verify builds the fixture `apply` and `withdraw` take 2.5 s so a case can see their progress, and so do the fixture `block_user` and `unblock_user` (the fixture board and detail hide a blocked poster's bounties; `-uiVerifyBlock failOnce` fails the first block and the first unblock); `apply.write_delay_s()` reads that delay from `services.ts`. `-uiVerifyApplyNote <text>` seeds the apply sheet's note for every bounty (non-ASCII the keyboard path cannot type); NSUserDefaults reads the value as a plist token, so it stops at the first space, and `-uiVerifyApplyNote worst` seeds a 140-code-point note with spaces (`WORST_NOTE` in `src/features/bounty/apply/fixtureNotes.ts`). `-uiVerifyDetail ok|failOnce|gone|notSelected|selected` makes the fixture detail load fail once or answer gone for every id, and the `bounty-detail` scene opens `-uiVerifyDetailId` (default `fixture-bounty-01`). `-uiVerifyBoardPlace none|sunway` seeds the fixture user's stored board origin at launch: `none` clears the chosen place and the 先不用 choice, `sunway` stores Sunway Geo Residences; omitted, both are kept, which is how the relaunch checks work. `-uiVerifyPlaces ok|none|fail|resolveFail` replaces the kit's MapKit place search (default `ok`: Sunway Geo Residences, Sunway University and Sunway Pyramid for any query; `none`: no results; `fail`: the first query fails and the next succeeds; `resolveFail`: picking a result or the current location fails). The verify post service writes the arguments of each accepted publish as JSON to the app's defaults key `uiVerifyPublishedArgs` (cleared at launch); `bounty.published_args(ui)` reads it from the app container, so a case can assert what was sent. The verify select service writes every `select` that answered ok (the server committed it, including a `-uiVerifySelect lostAnswer` commit whose answer the fixture then fails) to the defaults key `uiVerifySelectedArgs` as a JSON array of `{"bounty", "applicant"}` objects, cleared at launch; an array rather than one object, so a case can assert exactly one select. The fixture `select` takes 2.5 s like `apply`; `-uiVerifySelectDelayMs <ms>` sets another delay for one case (`bounty_select` uses 20000 so its screenshot lands while the send is still in flight: with the clip recording, `simctl io screenshot` took up to about 8 s), and `choose.write_delay_s(ui)` reads the argument when the case passes it.
`-uiVerifyApplicants three|none|one|fifty|worst` picks the applicant set behind the 挑人 screen (default `three`: 阿杰, Hana and Aiman; `none`: nobody; `one`: one applicant; `fifty`: fifty; `worst`: 40-character names, 128 helped, 140-code-point notes), and `-uiVerifyApplicantsFail none|first|refresh` fails the first applicant load or the first refresh once (default `none`). `-uiVerifySelect ok|failOnce|lostAnswer|taken|notPending|noPayee|closed` answers the fixture `select_helper` (default `ok`; `failOnce` fails the first call; `lostAnswer` commits the first call but answers `failed`, later calls behave like the RPC; `taken` means another device already chose 阿杰, so a hold on 阿杰 answers `ok` and a hold on anyone else answers `taken`; `notPending` drops that applicant from the list; `noPayee` and `closed` answer those reasons). The verify select service counts every `select` call it receives, rejected ones included, in the defaults key `uiVerifySelectAttempts` (cleared at launch), so `choose.assert_attempts(ui, n)` fails on an automatic replay. `-uiVerifyDetail notSelected|selected` (with `-uiVerifyDetailId`, default `fixture-bounty-01`) makes the fixture detail the applicant's outcome: `notSelected` is an applicant whose application was not chosen, with a note and no address; `selected` is the chosen helper with the exact address. The verify `markNotSelectedSeen` records each bounty id it receives as a JSON array in the defaults key `uiVerifyNotSelectedSeen` (cleared at launch). The shared fixture `block_user` takes 2.5 s; `-uiVerifyBlockDelayMs <ms>` sets another delay for one case (`bounty_applicant_block` uses 6000 so the progress state outlasts slow reads).
The `bounty-status` scene pushes the status screen for `-uiVerifyDetailId` (default `fixture-bounty-01`); the fixture status service reads `-uiVerifyBountyStatus open|assigned|assignedLate|enRoute|enRouteChanged|done|disputed|confirmed|markedPaid|settled|cancelled` (default `assigned`), `-uiVerifyBountyRole poster|helper` (default `poster`), `-uiVerifyBountyStatusLoad ok|firstFails|refreshFails|unavailable` (fail the first load, or the second load, which is the first refresh), `-uiVerifyBountyWaiver available|used`, `-uiVerifyBountyCharge free|coin` (what an open bounty's close gives back, default `free`), `-uiVerifyBountyPaymentId <id>` (the payment `confirm_bounty` answers; `fixture-owe` opens a payment the pay fixture knows) and `-uiVerifyBountyStatusDelayMs <ms>` (writes take 1.5 s by default) and `-uiVerifyBountyStatusFail <rpc>` (the first call of that RPC, such as `complete_bounty`, answers a network failure; later calls go through); every call it receives is a JSON array in the defaults key `uiVerifyBountyStatusCalls`, cleared at launch. The applicant list's 关掉这单 uses the same fixture status service, so a close case passes `-uiVerifyBountyStatus open`.
The hold gestures use `UI.press(identifier, seconds)` and `UI.press_at(frame, seconds)` in `driver.py` (`axe touch --down --up --delay`; each call costs about 1.2 s of overhead on top of `seconds`). `verification/ui/choose.py` is the bounty selection helper (named `choose.py` because a `select.py` would shadow the standard library module and break every case): `choose`, `hold_select`, `release_early`, `hold_reads`, `selected_args`, `wait_selected`, `assert_none_selected`, `assert_one_selected`, `attempts`, `assert_attempts`, `write_delay_s`, and the video analysis `fill_progress`, `label_split` and `analyse`.
`-uiVerifySignedIn [onboarded]` starts with the fixture session already signed in (with `onboarded`, onboarding is also done, so the app opens on home); `reach_home` then only waits for home. Cases that just need home, tabs or payee use it; only cases that test welcome, sign-in or onboarding go through welcome, and they call `ui.at_rest()` (or `sign_in_apple`) before tapping, because any continuous motion blocks `axe tap`.
`-uiVerifyQr <names>` replaces the screenshot picker and camera at the decode boundary: each pick
returns the next fixture in the comma-separated list (`duitnow`, `paying`, `dynamic`, `alipay`,
`wechat`, `none`), so a case can show an error and then a success. The system photo picker never
opens, so captures taken after an injected pick are named `injected-…` and the case docstring says so.
Without `-uiVerifyQr` the app uses the device source (expo-image-picker + `scanFromURLAsync`):
`payee_qr_real` adds the PNGs in `media/` to the Simulator library with `xcrun simctl addmedia`
before each pick, finds the picker cell by the image's tint (Alipay `#b8e4ff`, DuitNow TNG
`#ffd8a8` light modules) and taps it by coordinates, because the picker runs out of process and
`axe describe-ui` does not expose its cells. simctl cannot remove photos, so each image is added only once per
Simulator: `.verify/qr-media/<udid>` lists the images already added (`verify:clean` removes it, and the next run adds
them once more). The picker lists the oldest first, so the case swipes the grid up (at most 30 times, at rest between
swipes, distances taken from the screen frame) until a cell with the image's tint is in view; it does not depend on order
or count. The PNGs were made with segno
1.6.1 (scale 12, border 8); the DuitNow payload is a static TNG code for NURUL AINA BINTI AHMAD
with a valid CRC. Each run writes
`result.json` with commit, locale, Xcode, device, `videos` (every `.mp4` in the case folder; an empty one fails the run) and `duration_s` (wall-clock seconds of that
case, locale and appearance); the runner ends with a per-case timing table and the total, and
`verify:build` prints its own wall-clock seconds.
`log.txt` lists every AXe call with its duration; a timeout message adds the median call time,
which separates a slow Simulator from a stuck screen. A case gets 180 s unless it declares
`BUDGET = <seconds>`. Three consecutive runs on one Simulator that fail with the same timeout class (screenshot, `axe <command>`, or the case budget) stop the whole run with a render server CPU sample; `python3 -m unittest test_breaker` in `verification/ui` covers the rule. Only one `verify:ui` run may drive the Simulators at a time; a second run
exits instead of interleaving taps with the first. Every run also takes the machine-wide lock `/tmp/ios-ui-verify.lock` shared with other projects' runners and waits while another project holds it, printing the holder. The lock does not cover `verify:build` or
scripts that drive the Simulator outside the runner. Do not click or scroll in the Simulator window
while a run is in progress: a pointer drag reaches the app as a real touch, and a home case once
failed because a stray drag scrolled 悬赏 back to the top.

`ocr.find(ocr.lines(shot), pattern, within)` reads on-screen text with Vision (`ocr.swift`) for text inside a single
VoiceOver element, such as a board card whose parts have no frames of their own. Motion that must be timed uses
`recording.clip(ui, name)`: it pauses the run video (`run.mp4`, then `run-2.mp4`, …), records `<name>.mp4` around the
interaction, and `recording.frames(video, dir)` (`frames.swift`) returns each frame with its video timestamp, so the
timing does not depend on screenshot latency. Swift helpers compile once to `.verify/<name>` through `swifttool.py`.

Shell and home cases sign in through `reach_home`. `Shot` reads screenshot pixels in points, so
cases assert colours against `src/ui/theme/tokens.ts` (`token`, `assert_colour`), the 悬赏令 halo
(`glow`) and the 小貘 button outline (`assert_tapir_button`).

## Adding a case

1. Add or reuse a scene in `src/debug/scenes.tsx`; it calls `onReady` once settled, which shows
   the `ui-verify-ready` marker.
2. Write `cases/<name>.py`: docstring = behaviour sentence; `DEPS = [...]` path prefixes the case
   depends on (feature folders, routes, helpers such as `verification/ui/payee.py`; shared code and Debug scenes are
   implied, so `DEPS = []` is valid); `SCENE = '<id>'` if it starts from a scene (the runner launches with `-uiVerifyScene <id>`); optional `LOCALES = [...]`; wait on
   identifiers, assert, capture. Cases receive the locale as `ui.locale` for controls that only
   expose a localized label (native toolbar buttons); SwiftUI views from `@expo/ui` take their
   identifier from `testID` or the `accessibilityIdentifier` modifier.
3. Controls a case touches need a `testID`; plain `View`s also need `accessible` to appear in the
   accessibility tree.
4. Run both appearances and open the screenshots before reporting.
5. Reference the case from the acceptance criterion it proves in `docs/story-map.md`; the story-map
   check warns about a case no criterion references.
