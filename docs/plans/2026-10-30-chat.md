> cases but do not run them; the last task runs the selection once (Pace, 2026-10-29). When all tasks are done, run

**Status:** draft, 2026-10-30 (overnight). Waiting on questions 117–128 (canvas page 「05+ 消息与聊天」). The server
half that none of them decides (Task 1, 2026-11-03) is built; every other task waits for the answers.

**Goal:** A poster and the helper they selected, and later every accepted member of a ride, can message each other in
one thread per item: text and images, kept forever, with a fixed safety hint. Any message or person can be reported,
and either side can block the other from the thread.

**Architecture:** Supabase tables `threads`, `thread_members`, `messages`, `reports` with RLS and `security definer`
RPCs; threads are created by the bounty (and later ride) transition functions, never by clients. Live updates use
the shared layer in `docs/specs/2026-10-31-realtime-push-design.md`: a `chat.message` event on each recipient's
`user:<uid>` topic, handled in `src/lib/live/`, which reloads the open thread and the 消息 tab. Client feature `src/features/chat/` (tab list,
thread screen, report sheet); the block client moves to `src/features/block/` so bounty, chat and carpool share it.

**Tech stack:** Expo SDK 57, React Native 0.86, Expo Router, Supabase (Postgres 17, Realtime, Storage), bun test,
pgTAP, `verification/ui` (AXe).

**Spec:** `docs/specs/2026-10-11-foundation-design.md` (Decisions 「Chat」, Behaviour 「Chat」, Implementation order 7),
`docs/specs/2026-10-11-bounty-design.md` (decision 8A, P3, Known limits 「v1 has no chat」), carpool spec (group chat
later). Story map: `chat.thread.*`, `chat.safety.report`, `chat.block.*`.

## Decided (do not re-ask)

- One thread per bounty (poster + selected helper) and per ride (organiser + accepted members); members only; text
  and images; both reportable (F8); kept indefinitely (foundation).
- No chat before selection: an application carries one short note (bounty 8A). So a bounty thread opens at
  `assigned`, not at `open`.
- Fixed hint in new threads about deposits and paying outside the pay step (foundation Chat · Safety).
- Long-press a message → 翻译 / 举报 (foundation). 翻译 and 问小貘 reply drafts consume 小貘体力 and arrive with step 8;
  a draft is sent only on 发送.
- Account deletion removes the user's messages and keeps the other side's thread (F10).
- Blocks: `blocks`, `block_user`, `unblock_user`, `is_blocked_between` exist (`20261026000100_blocks.sql`); either side
  blocking means both are hidden from each other's bounties (bounty follow-up 6A).
- No chat home composer or permanent composer bar (N3+E). The 消息 tab exists with a badge wired to
  `feed.unreadMessages` (`src/app/(tabs)/_layout.tsx:35`).
- Freshness: the shared live-update layer (`docs/specs/2026-10-31-realtime-push-design.md`, Broadcast signals on
  `user:<uid>`, refetch through RPCs, no Postgres Changes); the freshness rule stays as the fallback.
- Push for `chat.message` goes through the same `events` outbox and `notify`; until the developer account exists it
  uses the `RecordingSender`, and the badge and the tab update in the app.
- AI suggestions on the 消息 tab sheet already exist as copy (`shell.ask.suggestions.messages`).

## Gaps found while preparing

1. **Report target.** The foundation says "report and block on every profile and message", but no profile screen
   exists (bounty 37A: the poster row is not tappable until one does). Asked as 127.
2. **Block inside a thread.** Blocking today hides bounties. Inside an existing thread it must also stop sending, and in
   a ride group it cannot remove a member. Asked as 123; group rule in Rulings.
3. **Report queue.** "Disputes go to a founder-run report queue" (foundation Known limits) has no tool. Ruling: a
   `reports` table and a service-role SQL view; no admin UI in this step.
4. **Delivery truth.** Data integrity says an acknowledgement means delivered and writes are never replayed
   automatically. Messages need a client id for an idempotent manual retry, and visible sending / failed states.
   Asked as 120.
5. **Thread screen quality.** RN has no built-in chat keyboard handling (interactive dismiss, growing input, inverted
   list). `react-native-keyboard-controller` is not installed. Asked as 128 with a spike as Task 0.
6. **Read state.** `last_read_at` per member is needed for the badge either way; whether the other side sees 已读 is a
   product choice. Asked as 125.

## Rulings (overnight, overturnable)

- Thread creation: `private.ensure_thread(kind, item)` called from `select_applicant` (bounty) and later the ride
  accept transition; members are added by the same functions. A thread is never deleted; a cancelled or settled item
  keeps its thread writable (the spec says "kept indefinitely"; a closed item may still need a word).
- Message limits: body ≤ 2000 characters, one image per message (≤ 10 MB before upload, re-encoded to JPEG 2048 px on
  device); images in a private bucket readable by thread members; signed URLs.
- Idempotency: `messages (sender_id, client_id)` unique; the client keeps a failed message on the device with its
  client id and sends it again only when the user taps it.
- Group block rule (rides): blocking a co-member does not remove anyone; the blocker sees the blocked person's messages
  collapsed as 「已屏蔽的人发的消息」 with 显示; the blocked person can still post to the group.
- Report reasons: 骚扰或威胁 / 要求站外付款或定金 / 不当内容 / 其他, plus an optional note ≤ 500; a report snapshots the
  reported message body and image path so a later deletion does not erase evidence.
- Moderation access: the report row and its snapshot are readable only by the service role; proofs and images are
  reachable through the same view.
- Unread: `thread_members.last_read_at`; the thread screen marks read on appear and on each new message while open;
  `unread_threads()` returns the count for the badge.

### ★ Server defaults (Task 1 server half, 2026-11-03, overturnable)

- Threads are created by triggers in the same transaction as the transition, not inside `select_helper` and
  `decide_ride_request`: a bounty's `open → assigned` (poster and helper) and a ride member's change to `accepted`
  (organiser and that member). The organiser's own row at publish creates nothing, so a ride thread starts with the
  first accepted rider. Existing assigned bounties and rides with accepted riders are backfilled.
- A ride member who leaves, withdraws or is declined (including memberships ended by a block before 出发) keeps the
  thread up to `left_at`: reads the history before leaving, cannot send (`not_member`), gets no events. Accepted again,
  they rejoin and see the whole thread.
- A non-member reading or sending gets `thread_not_found` (P0002), the same as a missing thread, so a thread's
  existence is not revealed.
- Bounty thread: a block in either direction stops both sides sending (`blocked`, 42501); the history stays readable.
  Ride group: sending is unaffected (group block rule above); the blocked pair get no `chat.message` events for each
  other's messages. What each side sees is still 123.
- `send_message(thread, client_id, body)`: body trimmed, 1–2000 characters; a resend with the same `client_id` answers
  with the stored message and emits nothing; the same `client_id` with other content or another thread is
  `client_id_reused`. `chat.message` events carry the thread id as `subject_id`, one per active member but the sender.
- `report(target_user, message, reason, note)`: reason optional (`harassment`, `off_platform_payment`,
  `inappropriate`, `other`) so 122 can still be one tap; note ≤ 500. A repeat report of the same message (or of the
  same person without a message) by the same reporter answers with the first. Reporter and target ids are set null on
  account deletion; the snapshot stays. No client grant on `reports`; the founder reads `private.report_queue`
  (service role only).
- `list_threads()` orders by the latest visible message, else the thread's creation, newest first (provisional for
  117). `read_thread(thread, before, max_count)` pages newest first by message id cursor, 1–100 per page.
- Clients may `select` threads, memberships and visible messages directly (members-only RLS) but never write; the RPCs
  are the main path.
- Account deletion needs no Edge Function change: messages and memberships cascade with `auth.users`.
- Message and membership times use `clock_timestamp()` so messages sent in one transaction keep their order and
  `left_at` compares correctly with them.
