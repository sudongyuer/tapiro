# Foundation step 7: chat with report and block

> **For agentic workers:** execute task by task. Only one Simulator-using agent runs at a time. Tasks write their UI
> cases but do not run them; the last task runs the selection once (Pace, 2026-10-29). When all tasks are done, run
> `spec-lifecycle` (foundation spec, step 7 record) before the PR.

**Status:** ready, 2026-11-05. Questions 117–128 (canvas page 「05+ 消息与聊天」) are answered with the ★ in
`docs/research/2026-11-03-chat-references.md` §2 (owner, 2026-11-05: 「都按推荐」; 125 is B). The server half of Task 1
(2026-11-03), report snapshot retention (2026-11-05), the shared block module (Task 2) and the chat client core with
read state (Task 3, 2026-11-06), the thread spike (Task 0), the 消息 tab list (Task 4, 2026-11-06) and the thread screen
without images (Task 5, 2026-11-06) and report and block (Task 6, 2026-11-06) are built; images (Task 5b) and Tasks 7–8 are next.

**Goal:** A poster and the helper they selected, and later every accepted member of a ride, can message each other in
one thread per item: text and images, kept forever, with a fixed safety hint. Any message or person can be reported,
and either side can block the other from the thread.

**Architecture:** Supabase tables `threads`, `thread_members`, `messages`, `reports` with RLS and `security definer`
RPCs; threads are created by the bounty (and later ride) transition functions, never by clients. Live updates use
the shared layer in `docs/specs/2026-10-31-realtime-push-design.md`: a `chat.message` event on each recipient's
`user:<uid>` topic, handled in `src/lib/live/`, which reloads the open thread and the 消息 tab. Client feature `src/features/chat/` (tab list,
thread screen, report sheet); the block client moves to `src/features/block/` so bounty, chat and carpool share it.

**Tech stack:** Expo SDK 57, React Native 0.86, Expo Router, Supabase (Postgres 17, Realtime, Storage), bun test,
pgTAP, `verification/ui` (AXe).

**Spec:** `docs/specs/2026-10-11-foundation-design.md` (Decisions 「Chat」, Behaviour 「Chat」, Implementation order 7),
`docs/specs/2026-10-11-bounty-design.md` (decision 8A, P3, Known limits 「v1 has no chat」), carpool spec (group chat
later). Story map: `chat.thread.*`, `chat.safety.report`, `chat.block.*`.

## Decided (do not re-ask)

- One thread per bounty (poster + selected helper) and per ride (organiser + accepted members); members only; text
  and images; both reportable (F8); kept indefinitely (foundation).
- No chat before selection: an application carries one short note (bounty 8A). So a bounty thread opens at
  `assigned`, not at `open`.
- Fixed hint in new threads about deposits and paying outside the pay step (foundation Chat · Safety).
- Long-press a message → 翻译 / 举报 (foundation). 翻译 and 问小貘 reply drafts consume 小貘体力 and arrive with step 8;
  a draft is sent only on 发送.
- Account deletion removes the user's messages and keeps the other side's thread (F10).
- Blocks: `blocks`, `block_user`, `unblock_user`, `is_blocked_between` exist (`20261026000100_blocks.sql`); either side
  blocking means both are hidden from each other's bounties (bounty follow-up 6A).
- No chat home composer or permanent composer bar (N3+E). The 消息 tab exists with a badge wired to
  `feed.unreadMessages` (`src/app/(tabs)/_layout.tsx:35`).
- Freshness: the shared live-update layer (`docs/specs/2026-10-31-realtime-push-design.md`, Broadcast signals on
  `user:<uid>`, refetch through RPCs, no Postgres Changes); the freshness rule stays as the fallback.
- Push for `chat.message` goes through the same `events` outbox and `notify`; until the developer account exists it
  uses the `RecordingSender`, and the badge and the tab update in the app.
- AI suggestions on the 消息 tab sheet already exist as copy (`shell.ask.suggestions.messages`).

## Gaps found while preparing

1. **Report target.** The foundation says "report and block on every profile and message", but no profile screen
   exists (bounty 37A: the poster row is not tappable until one does). Asked as 127.
2. **Block inside a thread.** Blocking today hides bounties. Inside an existing thread it must also stop sending, and in
   a ride group it cannot remove a member. Asked as 123; group rule in Rulings.
3. **Report queue.** "Disputes go to a founder-run report queue" (foundation Known limits) has no tool. Ruling: a
   `reports` table and a service-role SQL view; no admin UI in this step.
4. **Delivery truth.** Data integrity says an acknowledgement means delivered and writes are never replayed
   automatically. Messages need a client id for an idempotent manual retry, and visible sending / failed states.
   Asked as 120.
5. **Thread screen quality.** RN has no built-in chat keyboard handling (interactive dismiss, growing input, inverted
   list). `react-native-keyboard-controller` is not installed. Asked as 128 with a spike as Task 0.
6. **Read state.** `last_read_at` per member is needed for the badge either way; whether the other side sees 已读 is a
   product choice. Asked as 125.

## Rulings (overnight, overturnable)

- Thread creation: `private.ensure_thread(kind, item)` called from `select_applicant` (bounty) and later the ride
  accept transition; members are added by the same functions. A thread is never deleted; a cancelled or settled item
  keeps its thread writable (the spec says "kept indefinitely"; a closed item may still need a word).
- Message limits: body ≤ 2000 characters, one image per message (≤ 10 MB before upload, re-encoded to JPEG 2048 px on
  device); images in a private bucket readable by thread members; signed URLs.
- Idempotency: `messages (sender_id, client_id)` unique; the client keeps a failed message on the device with its
  client id and sends it again only when the user taps it.
- Group block rule (rides): blocking a co-member does not remove anyone; the blocker sees the blocked person's messages
  collapsed as 「已屏蔽的人发的消息」 with 显示; the blocked person can still post to the group.
- Report reasons: 骚扰或威胁 / 要求站外付款或定金 / 不当内容 / 其他, plus an optional note ≤ 500; a report snapshots the
  reported message body and image path so a later deletion does not erase evidence.
- Moderation access: the report row and its snapshot are readable only by the service role; proofs and images are
  reachable through the same view.
- Unread: `thread_members.last_read_at`; the thread screen marks read on appear and on each new message while open;
  `unread_threads()` returns the count for the badge.

### ★ Server defaults (Task 1 server half, 2026-11-03, overturnable)

- Threads are created by triggers in the same transaction as the transition, not inside `select_helper` and
  `decide_ride_request`: a bounty's `open → assigned` (poster and helper) and a ride member's change to `accepted`
  (organiser and that member). The organiser's own row at publish creates nothing, so a ride thread starts with the
  first accepted rider. Existing assigned bounties and rides with accepted riders are backfilled.
- A ride member who leaves, withdraws or is declined (including memberships ended by a block before 出发) keeps the
  thread up to `left_at`: reads the messages and the roster as they were when they left, cannot send (`not_member`),
  gets no events. Rejoining is unreachable today (`request_ride` accepts a new request only after a withdrawal, and a
  withdrawn requester was never a thread member); if that changes, `ensure_thread` clears `left_at`. A bounty thread
  marks anyone but the poster and the new helper as left at `assigned`, so it never holds a third active member.
- A non-member reading or sending gets `thread_not_found` (P0002), the same as a missing thread, so a thread's
  existence is not revealed.
- Bounty thread: a block in either direction stops both sides sending (`blocked`, 42501); the history stays readable.
  Ride group: sending is unaffected (group block rule above); the blocked pair get no `chat.message` events for each
  other's messages. What each side sees is still 123.
- `send_message(thread, client_id, body)`: surrounding whitespace (spaces, tabs, newlines, no-break and
  zero-width spaces U+00A0, U+200B, U+FEFF) trimmed in the function and
  enforced by the table check, 1–2000 characters; the caller's membership row is locked `for share` while sending; a resend with the same `client_id` answers
  with the stored message and emits nothing; the same `client_id` with other content or another thread is
  `client_id_reused`. `chat.message` events carry the thread id as `subject_id`, one per active member but the sender.
- `report(target_user, message, reason, note)`: reason optional (`harassment`, `off_platform_payment`,
  `inappropriate`, `other`) so 122 can still be one tap; note ≤ 500. A repeat report of the same message (or of the
  same person without a message) by the same reporter answers with the first. Reporter and target ids are set null on
  account deletion; the snapshot stays. No client grant on `reports`; the founder reads `private.report_queue`
  (service role only).
- `list_threads(before, max_count)` orders by the latest visible message, else the thread's creation, newest first
  (provisional for 117), 50 per page by default (1–100), with `hasMore` and an opaque `nextCursor` holding the last
  row's sort key, so a thread that gets a new message between pages is neither repeated nor skipped.
  `read_thread(thread, before, max_count)` pages messages newest first by message id cursor (a message's time never
  changes).
- Clients may `select` threads, memberships and visible messages directly (members-only RLS) but never write; the RPCs
  are the main path.
- `private.thread_visible_until(thread)` reads `auth.uid()` itself; it stays executable by `authenticated` because the
  RLS policies call it as the querying role (it is `security definer` so the `thread_members` policy does not recurse).
- Report snapshot retention (owner ★ 2026-11-05): a report's copy of the message (`message_body`, `message_sent_at`)
  is cleared one year after the report by `public.expire_report_snapshots()`, run daily at 03:15 Malaysia time by
  pg_cron (`report-snapshots-daily`, `supabase/migrations/20261105000200_report_snapshot_retention.sql`), the same
  mechanism as the events cleanup. ★ by default, owner may veto: the report row itself (reason, note, the ids that are
  still set) stays for the moderation history. When images land (124), the snapshot's image path and its object are
  cleared by the same rule.
- A chat push never shows the message text: 「{name}发来一条消息」 titled by the bounty or the ride route. Whether a
  lock-screen preview shows the text is a product choice to raise with 120/125.
- Account deletion needs no Edge Function change: messages and memberships cascade with `auth.users`.
- Message and membership times use `clock_timestamp()` so messages sent in one transaction keep their order and
  `left_at` compares correctly with them.

### ★ Client core defaults (Tasks 2–3, 2026-11-06, ★ by default, owner may veto)

- Mark read: the store marks an open thread read up to the newest message it has shown (`mark_read(thread, message)`),
  not up to the server's now, so a message stored after the screen loaded stays unread until it is shown. A thread
  that is not open is never marked. The read time only moves forward.
- 已读 (125 B): bounty threads only; `peerReadAt` is null in ride groups, and members cannot read `last_read_at` from
  the table (column grant), so a ride group never reveals who read what; a blocked pair do not see each other's read
  time. A read in a bounty thread sends the other
  member a live-only `chat.read` (no push) so 已读 appears while the thread is open; nothing for ride groups.
- Unread: a thread is unread when it holds a message from someone else after your read time; your own messages,
  messages after you left, and messages from someone blocked in either direction never count. The 消息 badge is the
  number of unread threads (`unread_threads()`), refreshed on sign-in, every `chat.message`, reconnect, return to the
  foreground and after each mark. A failed refresh keeps the last count (shown as stale in the store); before the
  first answer the badge stays hidden. The store's local `unread` flag after a mark does not know about blocks (the
  server's count does) and is corrected by the next reload. Known limit: reading on one device does not signal your other devices (events
  skip the actor), so their badge catches up on their next refresh.
- Outbox: a message is written to the device (`Settings`, `tapiro.chatOutbox.<uid>`) before the request, as sending.
  A failed send stays as failed with its reason (`blocked`, `notMember`, `notFound`, `invalid`, `clientIdReused`,
  `failed`); one still sending when the app stopped comes back failed, since its outcome is unknown. Only the user's
  tap retries, with the same client id, or discards it. A thread load that shows a waiting message's client id as
  stored settles it without sending. The outbox is per user, kept across sign-out, cleared on account deletion.
- Order in a thread: waiting and failed messages sit below every stored message, newest written last, since they have
  no server position yet; stored messages follow the server order. A stored message keeps its client id as its list
  key, so a bubble does not remount when it turns from sending to stored.
- Freshness: `chat.message` reloads the badge, the thread list if loaded and the thread if open; a thread that is not
  open goes stale (only from loaded data; a failed thread stays failed) and reloads when opened; your own send reloads
  the thread so a read already in flight cannot hide the new message; `chat.read` reloads only the open thread; reconnect and return to the
  foreground reload everything loaded. A reload keeps older pages already shown when the newest page joins them, and
  drops them when there is a gap.
- Verify mode: `uiVerifyChat=1` lets the fixture chat service drive the 消息 badge; without it the shell feed's fixture
  badge stays, so existing shell cases are unchanged. Fixtures follow `uiVerifyFixture` (demo: three threads, one
  unread; one; empty; worst: 61 threads, a 2000-character message, a 56-character name); `uiVerifyChatFail` fails the
  first call of `list`, `thread`, `send`, `unread`, `markRead` or `report`; calls are recorded in `uiVerifyChatCalls`.
- Left open for Task 4–5: list rows and the pinned item card still need the item's title and art in `list_threads` /
  `read_thread` (117 A, 118 A), images (124 A), and the `chat.*` tap route moves from 消息 to the thread once the
  screen exists. The list reload on each `chat.message` keeps only the first page and `loadMoreThreads` waits while
  the list is stale; Task 4 decides whether loaded pages should be kept.

### ★ 消息 list defaults (Task 4, 2026-11-06, ★ by default, owner may veto)

- Server: each thread's JSON has `item`: a bounty's `title`, `category`, `art` and `status`, or a ride's `from`, `to`
  (the 8-character shorts), `departsAt` and `status`. It is in `read_thread` too, for the pinned card (118 A).
- Rows sit in one inset grouped card, newest first: the 40 pt hand art (a bounty's chosen art, else from its title and
  category, as everywhere else; a ride's car), then line 1 the title (semibold, one line) · the other side (at most 45%
  of the line, so a long title never hides it) and the time; line 2 the last line, one line, in label colour while
  unread, with a red dot (system red, the colour of the tab badge, as drawn for 117 A) at its end.
- The other side: a bounty's other member (「对方」 when the name is missing); a ride group's 「N 人」 counting the active
  members and you; 「你已离开」 for a group you left. The last line: yours as 「我：…」, a group member's as 「名字：…」, a
  bounty peer's bare; line breaks fold into spaces; 「还没有消息」 for a thread without messages.
- Time: the clock today, 昨天, the weekday within six days, then the short month and day (with the year for another year), measured
  from the time the list loaded.
- Empty: a moment screen (moment ground, the 148 pt front 小貘, 「还没有消息」, one line, a secondary 「去看看悬赏」 that opens
  悬赏). Pull to refresh works on it and on the list.
- First load failed: the inline 「消息没加载出来，请检查网络后重试」 card with 重试, never the empty screen. A failed refresh
  keeps the rows under the warning card 「可能不是最新 · hh:mm 的数据」 with 重试 (the pay sheet's copy). While the live channel
  is dropped, 「可能不是最新」 sits above the rows (realtime 171 A; 消息 is a screen where someone waits).
- Paging: the next page loads when the end is within one screen; a failed page shows 「更早的对话没加载出来」 with 重试
  under the rows and is retried only by that tap, not by scrolling (hidden while the list is not current; the warning
  card's 重试 reloads). A reload (each `chat.message`, pull, reconnect, foreground) asks again for as many rows as are
  shown (`list_threads(null, n)`, at least 50, at most 100) and replaces the list, so a late-joined ride thread with an old
  sort key, a deleted thread or a changed name is never kept from an older answer; past 100 rows the list returns to
  its first 100.
- `item.status` is the status the user is shown: `private.bounty_status` (`settled` once paid) and `private.ride_phase`
  (the clock's gathering or expired). A member who left a thread still sees the item as it is now (title, status), as
  the bounty and ride RLS already lets them read it.
- A row pushes `/messages/[thread]` and stays selected until the return transition deselects it. The thread is titled by
  the other side, or the route for a ride group. A `chat.*` notification tap still opens the 消息 tab; Task 5 moves it to
  the thread.
- Time and dates: older rows read as a short month and day (`Oct 30`, 「10月30日」, `30 Okt`).
- Known limits: a long title truncated next to a long name can leave a small gap before 「·」 (iOS truncation inside a
  shrunk text box); the row times do not tick past midnight until the next reload.

### ★ Thread screen defaults (Task 5, 2026-11-06, ★ by default, owner may veto)

- 120 A follows the canvas drawing, not the shorter wording in the Answers list: the canvas ★ (ChatPick1, 120 A) is the
  WeChat style, 「气泡本身不变淡」, a spinner beside a bubble that is still sending, nothing once stored, a red ! when it
  failed. So bubbles do not dim. The spinner appears only after 0.5 s, so a normal send does not flash it. Tapping !
  asks 「重发该消息？」 with 重发, 删除 and 取消 (删除 added so a message that can never go out does not stay forever); a
  refused message (`blocked`, `notMember`, `notFound`, `invalid`, `clientIdReused`) offers only 删除 and 取消
  (「这条消息发不出去」), since resending cannot succeed. Veto option: dim while sending as the Answers list words it.
- 118 A: the item card is a fixed bar under the navigation bar, outside the scroll view (the transcript scrolls below
  it, not under it), on `secondarySystemBackground`: 30 pt art, the title on one line, the status the user is shown
  (bounty) or 「今天 14:30 出发 · 集合中」 (ride), and 看详情. The whole card is one button. It pushes the bounty status
  screen or the ride detail in their own tabs, as notification taps do (the 消息 tab turns off automatic content insets
  for the keyboard, so those screens are not pushed inside it). A glass card floating over the transcript was tried

- 119 A: the safety card is the first row of the transcript (scrolls away with it), shown once every older page is
  loaded: the 32 pt front 小貘 on the moment ground, the canvas copy. No close control.
- 121 A: the system context menu through a new kit view (`ContextMenuView`, `UIContextMenuInteraction`; the bubble
  itself lifts as the preview, rounded to the bubble). `@expo/ui` `ContextMenu` was tried first: a SwiftUI bubble in a
  `matchContents` Host measured shorter than it drew for a 2000-character message, so the next row overlapped it. Other
  people's messages: 复制, then 举报 in its own last group; your own: 复制 only; no 翻译 until step 8, no unsend. The
  same actions are VoiceOver custom actions on the bubble. Until Task 6's reason sheet, 举报 asks 「举报这条消息？」 and

- 125 B: 「已读 14:08」 under your newest stored message when the other side's read time has reached it, bounty threads
  only; the time reads like the list rows (clock today, 昨天, weekday, date).
- Tab bar: hidden while a thread is open (and the urgent accessory with it), back when you leave; root sheets such as
  the pay sheet keep it hidden.
- Composer: grows to 5 lines, then scrolls (spike). Its text is a draft kept on the device per user and thread
  (`tapiro.chatDrafts.<uid>`), restored when the thread opens again and across restarts, cleared when it is sent (after
  the message is in the outbox) and on account deletion.
- Read: a thread is marked read while it is focused (open and on top) and the app is active, not while a pushed
  screen covers it or the app is in the background (the peer would otherwise see 已读 for an unseen message); new
  messages arriving while focused are marked too, and returning to the foreground marks the open thread.
- Transcript: a centred time line before the first message and before any message an hour or more after the previous
  one (clock today, else 「昨天 20:00」 / weekday / date with the clock). In ride groups the speaker's name sits above
  their bubble when the speaker changes; bounty threads show no names.
- States: first load shows a spinner; a failed first load shows 「对话没加载出来」 with 重试 and no composer, never an empty
  thread; a failed refresh keeps the messages with 「可能不是最新 · hh:mm 的数据」 and 重试 under the item card; a dropped
  live channel shows 「可能不是最新」 there; a failed older page shows 「更早的消息没加载出来」 with 重试 at the top, retried
  only by that tap. A ride member who left sees 「你已离开这个拼车，不能再发消息」 in place of the composer.
- Push: a `chat.*` notification tap opens that thread, with the 消息 list under it (the stack's anchor); a tap for the
  thread already open does not stack it twice (`navigate`).
- Known limits: no image messages yet (Task 5b); the context menu preview, VoiceOver order and keyboard feel are device
  checks (spike list).
