# Coin purchase (IAP) built and tested locally, before the paid account

> **For agentic workers:** execute task by task. Tasks marked **now** need no Apple Developer Program membership, no
> App Store Connect and no hosted Supabase; tasks marked **account** wait on the paid account. Only one
> Simulator-using agent runs at a time. Tasks write their UI cases but do not run them; the last **now** task runs the
> selection once (Pace). When the **account** tasks are done, run `spec-lifecycle` (foundation spec, step 5 purchase
> record) before the PR.

**Status:** proposed 2026-11-11. Owner answered 268–272 and 279 on 2026-11-11 and 273–278 on 2026-11-12 (「Answers」
below). Task 3 (server) and the receiver half of Task 9 are built (branch `feat/iap-server`); Tasks 1 and 2 (spikes) are
done (branch `spike/iap-live-activity`, 「Spike results」 below); Tasks 4 and 5 are built (branch `feat/buy-coins`,
「Client and purchase UI as built」 below), and Task 6 runs through the StoreKit harness except the refund. Tasks 7–10
wait on the paid account.

**Goal:** A user whose free posts are used up can buy a coin pack with the native StoreKit sheet, and the coins land
in the ledger only after the server has verified the transaction. Before the account exists the whole path runs on
the Simulator against Xcode's local StoreKit test environment and the local Supabase stack; the account only swaps the
signing root and adds sandbox, server API and server notification paths.

**Architecture:** A StoreKit 2 wrapper in `modules/tapiro-kit` (products, purchase, transaction updates, finish)
behind the kit facade; `src/features/coins/purchase` (pack list, pending state, service, fixture service for verify
mode); an `iap-verify` Edge Function that verifies the signed transaction (JWS) and calls one `security definer` RPC
that writes `iap_transactions` and a `purchase` ledger row in one transaction; a config plugin that attaches a local
`.storekit` file to the generated Xcode scheme.

**Tech stack:** Expo SDK 58, React Native 0.88, Swift (StoreKit 2, iOS 26.0+), Supabase Edge Functions (Deno),
Postgres 17, pgTAP, `bun test`, Deno tests.

**Spec:** `docs/specs/2026-10-11-foundation-design.md` (Decisions 「Coins: purchase」, 「Coins: spend」, 「Ledger」,
「Account deletion」; Behaviour 「貘币」; Data flow `iap_transactions`, `iap-verify`; Errors 「IAP verification fails or is
pending」; Implementation order 5; Open point 「IAP library and server-side transaction verification」). Earlier plan:
`docs/plans/2026-10-30-coins-reputation-remaining.md` (step 5 item 1, 「Blocked on the user」). Story map:
`coins.purchase.packs`, `coins.purchase.short`, `coins.purchase.sandbox`.

## Gaps found while preparing

1. **The `.storekit` file reaches Xcode only through the scheme.** `ios/` is generated, so the scheme setting must come
   from a config plugin (AGENTS.md). If `expo run:ios` ignores it (sources above), local purchases run only when the
   app is launched from Xcode (`xed ios`, Run). Task 1 measures this on Xcode 27.2 before anything relies on it.
2. **UI cases cannot drive the real StoreKit sheet.** Verify builds start through `xcodebuild` and AXe; even if the file
   were applied, the system sheet is outside the app. UI cases use the fixture StoreKit boundary; the real path is a
   manual Xcode run now and a device checklist row later (`coins.purchase.sandbox`).
3. **The ledger has no purchase reasons.** `coin_reason` lacks `purchase` and a refund reason; ledger rows link items
   through `payment_item_kind`, which has no IAP kind. `delta` is capped at ±100, enough for 35.
4. **Local signatures are not Apple's.** Local JWS must never verify on the hosted project. The local path needs its
   own trust root (the certificate Xcode exports with Editor → Save Public Certificate) or the library's
   skip-for-Xcode path guarded by an environment flag that only the local stack sets.
5. **Refunds after spending.** A refunded pack may already be spent; the ledger can go negative unless a rule says
   otherwise. Asked as 268.
6. **Exact price points.** Whether RM5, RM10 and RM30 are exact Apple Malaysia price points is visible only in App
   Store Connect. Asked as 269.
7. **Ownership binding.** A transaction must be credited to the signed-in user, not to whoever posts the JWS first:
   pass `appAccountToken` = the user's UUID in the purchase options and check it on the server.
8. **Retry on launch vs 「never replay a write」.** The foundation spec says verification retries on the next launch.
   StoreKit itself re-delivers unfinished transactions; forwarding them is idempotent on `transaction_id`, and the user
   is never charged twice. This is the spec's own rule, not an automatic replay of a user write.
9. **Free allowance after a purchase.** Free posts are spent first (`spend_post`), so a buyer with free posts left
   keeps their coins; the no-balance sheet appears only with 0 free and 0 coins. No change needed; listed so it is not
   re-asked.

## Rulings (agent, for veto)

- **R1 Library: StoreKit 2 in the kit.** ★ Reason: consumables need six APIs; the kit rule; no third-party churn.
  Fallback: `expo-iap` if Task 2 hits a blocker in the kit within its time box.
- **R2 Finish after credit.** The app calls `finish()` only after `iap-verify` answers credited or already credited; a
  failed or offline verify leaves the transaction unfinished, and the UI shows 「购买处理中」.
- **R3 Idempotency.** `iap_transactions.transaction_id` is the primary key; a second verify of the same transaction
  answers the first result and writes nothing.
- **R4 Environments.** The hosted project accepts `Production` and `Sandbox` (App Review buys in the sandbox) and
  rejects `Xcode` and `LocalTesting`; the local stack also accepts `Xcode` when `IAP_ALLOW_XCODE=1`. Every row stores
  its environment.
- **R5 Product IDs** `app.tapiro.coins.5`, `app.tapiro.coins.11`, `app.tapiro.coins.35`; the coin amount comes from a
  server table keyed by product ID, never from the client.
- **R6 Verify-mode fixture** returns products, success, pending, cancelled, failed and refunded on demand, so UI cases
  cover every state without StoreKit.

## Server as built (Task 3 and the Task 9 receiver)

- Migrations `20261111000000_iap_coin_reason.sql` (`purchase`, `purchase_refund`, `purchase_refund_reversed`) and
  `20261111000100_iap.sql`: `iap_products` (the three packs, server config), `iap_transactions` (server only, no
  deletes), `iap_notifications` (one row per `notificationUUID`), `coin_ledger.iap_transaction_id` with one row per
  (transaction, reason). RPCs for the service role only: `iap_credit`, `iap_revoke`, `iap_apply_notification`.
- Edge Functions `iap-verify` (user JWT, body `{ signedTransaction }`) and `iap-notify` (no JWT, body
  `{ signedPayload }`, the App Store Server Notifications V2 shape); shared code in `supabase/functions/_shared/iap`.
  Contract in `supabase/README.md` 「In-app purchase」.
- **Apple's library does not run in the Supabase Edge Runtime.** `@apple/app-store-server-library` 3.1.0 verifies in
  Deno 2.9.8, but under `supabase functions serve` (edge-runtime 1.68.4 / Deno 1.45.2, and 1.77.8 / Deno 2.1.4 with
  `deno_version = 2`) its chain check throws `Not implemented: crypto.X509Certificate.prototype.toString` (and `.raw`,
  which it also reads), so every signed transaction would be rejected. A polyfill would need `raw`, which the runtime
  does not expose either. The functions therefore run a port of the library's `verifyJWT` and
  `verifyCertificateChain` (offline mode) on `jsrsasign` 11.1.5, which the library itself depends on, and `jose`
  6.2.16 for the ES256 signature; both were probed in both runtimes. `apple.deno-test.ts` runs Apple's library and the
  port on the same 17 fixtures (valid, tampered, other root, expired leaf, missing Apple marker on leaf or
  intermediate, intermediate not a CA, short chain, other app, other environment, unsigned, `Xcode`, notifications,
  Production app ID; after the #112 review also expired intermediate and root, a leaf not yet valid, a missing
  `signedDate` with a valid and an expired leaf, `alg: none` with and without a signature, an HS256 header keyed with
  the leaf certificate, and an unsigned notification around a signed transaction: 26 in all) and requires the same
  verdict. `tests/iap.integration.ts` also posts Sandbox transactions and notifications signed through a local test
  root to `supabase functions serve`, so the port's signed path is exercised inside the Edge Runtime itself. Source: https://github.com/apple/app-store-server-library-node
  (`jws_verification.ts`, v3.1.0).
- The bundled trust root is Apple Root CA - G3; its SHA-256 is pinned in `config.test.ts` and matches the copy in the
  macOS system root store.

### ★ Server defaults (agent, for veto)

- S1 Runtime verification is the port above, with Apple's library as the test oracle (reason: the library cannot run
  where the functions run; the port is about 140 lines on the library's own dependency).
- S2 Online checks (OCSP) are off, as in the library's `enableOnlineChecks: false`: certificate dates are checked at the
  transaction's `signedDate`. Revisit in Task 8 with real Sandbox data.
- S3 `Xcode` and `LocalTesting` are accepted only when `IAP_ALLOW_XCODE=1` **and** the function runs on the CLI's
  local stack, recognised by three independent conditions, all required: `SUPABASE_URL` is a local host (`kong`,
  `localhost`, `127.0.0.1`, `[::1]`, `host.docker.internal`); neither `SB_REGION` nor `DENO_DEPLOYMENT_ID` is set
  (Supabase sets them only in hosted functions, https://supabase.com/docs/guides/functions/secrets; a probe of
  `functions serve` on CLI 2.122.1 showed `SB_EXECUTION_ID` is set locally too, so it is not used); and
  `SUPABASE_SERVICE_ROLE_KEY` is the CLI's public demo key (`iss: supabase-demo`). A hosted project refuses them even
  with the flag (R4), and so does a server on a public VM that was given `local.env` and a `kong` URL but its own keys
  (#112 review). `supabase/functions/local.env` (was `ai-draft/fake.env`) sets the flag for `bun run fn:serve` and CI.
- S4 `Sandbox` is accepted everywhere (272 A, App Review); `Production` only once `IAP_APP_APPLE_ID` is set.
- S5 Only `type: Consumable` with `quantity: 1` is credited (the app never sets a quantity); anything else is 422.
- S6 `appAccountToken` must equal the caller's user id (gap 7), and a transaction belongs to the first user it was
  credited to; another user gets 403 and nothing is written.
- S7 One refund and one reversal per transaction, in any order with the app's credit; the buyer ends with the pack in
  all six orders (`supabase/tests/iap_order.test.sql`). `REFUND_REVERSED` gives the pack back once
  (`purchase_refund_reversed`); a refund after a reversal changes nothing more. A reversal for a transaction not seen
  yet is stored on a new row with `refund_reversed_at`, so a later refund is `duplicate` and the later credit pays; a
  reversal of a refund that reached the app before any credit pays the pack then (`purchase`). Before the #112 review
  an early reversal answered `unknown_transaction` and a later refund stored the purchase revoked forever: paid, no
  coins. Storing the row was chosen over answering non-200: Apple retries a failed notification only for about three
  days, and a reversal must also survive when the app verifies much later. A refund seen before the purchase was ever
  verified (and never reversed) is stored as revoked, and the purchase is then never credited.
- S8 Every notification is stored once by `notificationUUID` with its outcome; types other than `REFUND` and
  `REFUND_REVERSED` (`CONSUMPTION_REQUEST`, `TEST`, …) are recorded and ignored.
- S9 Account deletion keeps `iap_transactions` with `user_id` null; `appAccountToken` is never stored.
- S10 The `Sandbox` mark is `iap_transactions.environment`; since Task 5 `coin_history` exposes it as `sandbox` and the
  coins page labels the purchase rows (B9, B10).
- S11 The product table has no on/off flag: retiring a pack must not strand a purchase that was already paid.
- S12 The app finishes a StoreKit transaction only on a 200 (`credited`, `duplicate`, `revoked`); 4xx rejections, 503
  `verification_unavailable` and 5xx keep it unfinished (R2; Task 4 requirement).
- S13 On the local stack only (S3's conditions), `IAP_TEST_ROOT` adds a trust root next to G3, and `local.env` sets
  it to the committed test chain `supabase/functions/tests/iap-test-pki.json` (root, intermediate with the Apple
  markers, leaf and its key, valid to 2045). It lets the stack test sign Sandbox data the way Apple does; the key is
  public by design, so the gate is the same one as for `Xcode`, and a hosted config ignores the variable
  (`config.test.ts`).
